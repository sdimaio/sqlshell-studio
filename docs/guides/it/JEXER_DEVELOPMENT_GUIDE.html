Jexer Development Guide

Manuale pratico per sviluppare applicazioni TUI in Java con Jexer
Stile didattico ispirato ai manuali Borland Turbo Vision
Versione di lavoro: 1.2
Repository di riferimento: https://codeberg.org/AutumnMeowMeow/jexer
File complementari: JEXER_COMPONENT_REFERENCE.md, JEXER_COOKBOOK.md
Nota: alcuni nomi di metodi o costruttori possono variare leggermente tra versioni di Jexer. Gli esempi seguono la API Jexer 2.0 letta dal repository di riferimento.

Prefazione

Jexer è una libreria Java per costruire interfacce testuali ricche: finestre, menu, dialog, campi di input, liste, pulsanti e controlli custom dentro un terminale. Questa guida non è una javadoc travestita. È un manuale operativo pensato per insegnare a costruire applicazioni vere.

Torna all'indice

1. Cos'è Jexer

Jexer è una libreria TUI, non una semplice CLI. Gestisce focus, finestre, eventi e ridisegno dello schermo. È adatta a tool gestionali, browser di dati, editor e dashboard da terminale.

2. Modello mentale

  • TApplication: l'applicazione
  • TWindow: una finestra
  • Widget: i controlli
  • Eventi: input da tastiera o mouse
  • Model/Service: dati e logica fuori dalla UI

La UI non deve essere il tuo database. Deve raccogliere input e visualizzare stato.

4. Prima applicazione

package app;

import jexer.TAction;
import jexer.TApplication;
import jexer.TWindow;
import jexer.backend.BackendType;

public class HelloApp extends TApplication {

    public HelloApp() throws Exception {
        super(BackendType.XTERM);

        final TWindow window = addWindow("Hello Jexer", 2, 2, 50, 12);
        window.addLabel("Benvenuto in Jexer", 2, 2);
        window.addLabel("Questa è una vera finestra TUI.", 2, 3);
        window.addButton("Esci", 2, 5, new TAction() {
            @Override
            public void DO() {
                exit();
            }
        });
    }

    public static void main(String[] args) throws Exception {
        new HelloApp().run();
    }
}
L'inizializzazione del backend può variare a seconda dell'ambiente e della versione di Jexer.

10. Eventi

I callback devono essere piccoli. La logica vera va in metodi dedicati o service.

window.addButton("Salva", 2, 10, new TAction() {
    @Override
    public void DO() {
        onSave();
    }
});

private void onSave() {
    Customer customer = readForm();
    validate(customer);
    service.save(customer);
    showSavedMessage();
}

11. Dati e stato applicativo

private Customer readForm() {
    Customer c = new Customer();
    c.setName(nameField.getText());
    c.setEmail(emailField.getText());
    return c;
}

private void writeForm(Customer c) {
    nameField.setText(c.getName());
    emailField.setText(c.getEmail());
}

Lo stato non va letto e scritto dai widget in modo casuale. Usa metodi espliciti di binding.

12. Validazione

private void validate(Customer c) {
    if (c.getName() == null || c.getName().isBlank()) {
        throw new IllegalArgumentException("Il nome è obbligatorio");
    }
    if (c.getEmail() == null || !c.getEmail().contains("@")) {
        throw new IllegalArgumentException("Email non valida");
    }
}

Valida sia a livello UI che a livello business.

14. Widget personalizzati

public class StatusPanel extends TWidget {
    private String title = "";
    private String value = "";

    public StatusPanel(TWindow parent, int x, int y, int width) {
        super(parent, x, y, width, 3);
    }

    public void setTitle(String title) {
        this.title = title;
    }

    public void setValue(String value) {
        this.value = value;
    }

    @Override
    public void draw() {
        putStringXY(0, 0, "+------------------+");
        putStringXY(0, 1, "| " + title + ": " + value);
        putStringXY(0, 2, "+------------------+");
    }
}
Le primitive di drawing possono cambiare tra versioni. Il pattern resta valido: stato interno piccolo, rendering separato, API chiara.

15. Colori e tema visivo

Usa il colore per indicare focus, selezione, errore e stato. Evita combinazioni poco leggibili o significati incoerenti.

Per un look Turbo-like: sfondo scuro, finestre ben marcate, focus netto, status line evidente.

17. Architetture consigliate

Per applicazioni medie, una struttura MV-ish leggera è spesso la scelta migliore:

  • Model: dati
  • View: Jexer UI
  • Controller/Presenter: eventi e servizi

Evita la classe unica con tutto dentro.

18. Applicazione esempio

package app.model;

public class Note {
    private String title;
    private String body;

    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public String getBody() { return body; }
    public void setBody(String body) { this.body = body; }
}
package app.service;

import app.model.Note;
import java.util.ArrayList;
import java.util.List;

public class NoteService {
    private final List<Note> notes = new ArrayList<>();

    public List<Note> all() { return notes; }
    public void add(Note note) { notes.add(note); }
    public void remove(Note note) { notes.remove(note); }
}
package app;

import app.service.NoteService;
import app.ui.windows.MainWindow;
import jexer.TApplication;
import jexer.backend.BackendType;

public class MainApp extends TApplication {
    public MainApp() throws Exception {
        super(BackendType.XTERM);
        NoteService service = new NoteService();
        new MainWindow(this, service);
    }

    public static void main(String[] args) throws Exception {
        new MainApp().run();
    }
}

20. Checklist finale

  • UI separata da dati e servizi
  • callback piccoli
  • app usabile da tastiera
  • shortcut coerenti
  • resize tollerato
  • validazione presente
  • errori chiari
  • layout leggibile

Se queste condizioni sono soddisfatte, la tua app Jexer è già su basi solide.
